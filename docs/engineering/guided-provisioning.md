## Module interfaces and stage boundary

- `model.ts`: strict Effect Schemas for request, retained identity and journal; stage-specific safe errors/recovery; structured release handoff. Account IDs and UUIDs are installation inputs, never repository defaults. Tests use visibly synthetic values.
- `provider.ts`: injected transport behind the Effect `Provider` service. Reads the authorized account's existing workers.dev subdomain, Worker settings and explicitly identified D1; creates D1 only for an explicit fresh create. Uses exact `/accounts/{account}/workers/subdomain`, `/workers/scripts/{name}/settings`, `/d1/database/{uuid}` and POST `/d1/database` contracts. No listing accounts/databases, name guessing, provider login, retry of a POST, remote SQL, Worker upload or domain write. Timeout/redirect/network/HTTP/schema failures are fail-closed and dependency payloads are never reported.
- `provision.ts`: checks retained identity before provider calls, checks origin/Worker binding before create, durably records intent before a side effect and resolved identity before returning. A Worker with conflicting/multiple D1 bindings is refused. Repeated create against a resolved identity uses its ID, never creates replacement storage. A pending intent requires owner reconciliation and explicit bind, even if the original response failed before returning an ID. No attempt to infer that a missing response meant no resource was created.
- `identity-file.ts`: exclusive local lock, private mode0600 JSON, strict schema, fsync+atomic rename, external non-symlinked directory. No credentials in state. Stale lock or pending file fails closed; the owner must inspect/reconcile before removal. The lock coordinates **one local journal**, not provider Builds or multiple hosts; per-installation release serialization is WO-34. Keep one authoritative journal per installation, never run separate create journals for the same Worker.
- `cli.ts`/`main.ts`: local `plan` versus explicitly gated `provision`, cancellation and missing authorization fail before input/credential/provider access. No ambient provider fallback in tests. CLI confirmation/source flags attest owner intent, not independently proven grants. Main reads the securely supplied deployment token only after all remote gates; no login or broadening.

`provision` returns `status: provisioned-not-ready`, retained `identity`, `binding` (`DB`, exact D1 ID/name, migration directory), and Worker name/default workers.dev/canonical origin configuration. The Worker identity is a **target name**, not an uploaded Worker/version; the default origin is resolved from provider account configuration, not evidence the URL is live. Build, initialization, deployment and readiness remain `not-run`. WO-34 must consume this result rather than duplicate provisioning or manufacture ready status.

### Native button and CLI are different entry paths

The [official deploy-button page](https://developers.cloudflare.com/workers/platform/deploy-buttons/) states that the button clones the source into the owner's Git account, configures the project and uses Workers Builds; it provisions required resources and updates Wrangler configuration with identifiers such as D1 database IDs. Its Best practices section explicitly supports a custom package deploy script that runs migrations before `wrangler deploy`, and says migrations must reference the **binding name**, not the owner-editable database name. Our binding is `DB`. The documented pattern is feasible; a claim that the button cannot support migration-before-deploy is contradicted by this source.

The same page says that absent a package deploy script, the button preconfigures `npx wrangler deploy`. Root currently has no deploy script, so this fallback is **not** our approved ordered lifecycle. The CLI's explicit create-or-bind journal does not supply native button wiring. Do not copy CLI confirmation flags into Builds, insert CLI provisioning as a second writer after provider provisioning, or label these paths equivalent. Native entry should consume the provider-resolved binding from configuration; CLI entry should consume its retained identity. Both must converge on one validated installation target before migration/activation.

The button page also warns that a subdirectory URL makes that directory the new repository root and requires its dependencies to be isolated. Retain the repository-root entry for this one-Worker pnpm workspace, rather than switching the badge to `apps/forum` and dropping root tooling/dependencies. Its public-repository/source-authorization requirements are separate owner gates, not permission to change source visibility.

### What public docs do and do not establish about Builds

- [Build configuration](https://developers.cloudflare.com/workers/ci-cd/builds/configuration/) documents configurable build/deploy/root-directory settings, a selectable/generated API token, and separate build-only variables/secrets versus runtime variables. The documented generated-token permission list includes account settings, Workers scripts/KV/R2, routes and user/membership permissions; **D1 is not listed in that default list**. Do not infer D1 migration/create grants from that list, the button's provisioning capability, or a prior token. The selected token's genuine scope still needs coordinated owner proof.
- Its Default variables table lists `CI`, `WORKERS_CI`, `WORKERS_CI_BUILD_UUID`, `WORKERS_CI_COMMIT_SHA` and `WORKERS_CI_BRANCH`. This table does not establish injection of an account's default hosted URL, nor establish the exact credential/account environment made available to an arbitrary custom child process. Pinned Wrangler reads `CLOUDFLARE_API_TOKEN`/`CLOUDFLARE_ACCOUNT_ID`; that source-level contract is **not proof** that a particular Builds invocation supplies them with our required grants. Verify the supported handoff before choosing a concrete adapter; never log/read existing secrets to investigate it in this task.
- [Build limits](https://developers.cloudflare.com/workers/ci-cd/builds/limits-and-pricing/) defines concurrent-build limits **across an account** (currently1 free,6 paid). That is not an established per-installation release lock spanning native Builds and owner CLI, and cannot prove migration/activation serialization. The present local journal lock coordinates only one local file. A future authorized release implementation needs a reviewed serialization mechanism and local contention/failure tests; no paid service or new infrastructure choice is selected here.
- [Build image](https://developers.cloudflare.com/workers/ci-cd/builds/build-image/) documents version overrides and package-manager detection. Keep the pinned Node/pnpm/Wrangler toolchain and frozen install; do not substitute a floating `npx` installation for the workspace version.
