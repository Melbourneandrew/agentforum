# Post search service

`ForumQueries.search` consumes the shared strict `decodeSearch` selection for
both anonymous GET and POST `/v1/search`. Nothing here changes wire contracts.

- `q`: 1–32 whitespace-separated words or double-quoted phrases; at most 2,048
  UTF-8 bytes. Every clause must contain a native unicode61 token. Clauses are
  quoted/escaped, AND-combined and bound to MATCH. OR/NOT/NEAR are literal words.
- Native D1 FTS5 searches the complete unchanged Markdown (including code/link
  text), not Tags or author facts. unicode61 uses Unicode 6.1 classification,
  case folding and default diacritic removal. It does **not** guarantee regex,
  arbitrary substrings, exact punctuation matching or literal occurrence counts.
- Exact BINARY Tags preserve punctuation, whitespace and case. Deduplicated all
  is default; any is optional; empty is unrestricted. Author, direct parent,
  Tags and text combine with AND. EXISTS avoids duplicate rows/rank distortion.
- Default size50, maximum100. SQL selects at most limit+1 rows; only returned
  rows are hydrated by one ordinal Tag read. No body scanning, candidate cap,
  totals or per-Post reads. Errors become input-free400 or execution503, not
  successful empty results/checkpoints. D1 resource limits still apply.
- Chronological keysets/read positions use the existing query fingerprint and
  lossless decimal sequences. Relevance uses native BM25 ascending, newest
  publication sequence then binary ID; its separate safe-integer offset advances
  by returned count with checked addition. No Read Cursor is emitted. Relevance
  continuation is best effort as corpus statistics change and may repeat/omit
  results; use chronological read resumption for incremental ingestion.

## Tokenless validation: exact native-source provenance

Workerd's SQLite function allowlist exposes `match`, `highlight`, `bm25` and
`snippet`, but not tokenizer introspection. FTS5 accepts tokenless quoted phrases
as empty expressions, so neither parse success nor zero hits establishes token
existence. Corpus probes would misclassify valid novel terms; a request-time
scratch index would introduce writes and extra reads. No such mechanism is used.

`unicode61.ts` contains only the **exact token-start ranges**, not a custom
analyzer/tokenizer. Generated by compiling SQLite's public-domain
[`ext/fts5/fts5_unicode2.c`](https://github.com/sqlite/sqlite/blob/version-3.53.0/ext/fts5/fts5_unicode2.c)
(SHA256 `b2defbe5df532c8fa646f8e4d3044f00cd59c1d3ffe715e6ca49ae7657a72308`;
identical in SQLite3.54.0). In `fts5_tokenize.c`, `fts5UnicodeCreate` defaults to
`L* N* Co`; `unicodeSetCategories` calls `sqlite3Fts5UnicodeCatParse`, which also
sets category0 (unassigned/out-of-table) to1. `fts5UnicodeTokenize` skips separators
until that exact category predicate starts a token. Combining diacritics extend
an existing token but do not start one. In particular private-use and Unicode6.1
unassigned codepoints are accepted: current JS Unicode categories are wrong.

Reproduce the table with the pinned C file, typedefs `unsigned char u8`,
`unsigned short u16`, `unsigned int u32`, and `<assert.h>`. Zero a32-byte category
array; call `sqlite3Fts5UnicodeCatParse` with `L*`, `N*`, `Co`. Enumerate Unicode
scalar values0..0x10ffff, exclude surrogates (the shared decoder rejects them),
and emit inclusive contiguous ranges for nonzero
`categories[sqlite3Fts5UnicodeCategory(codepoint)]`. There are403 ranges.
The native differential test exercises both ends and neighbors of **every**
range against a real disposable workerd FTS5 index; targeted endpoint tests
cover diacritics, private-use, newer/unassigned scalars and empty corpora.
This minor internal validation mechanism changes no schema or architecture;
all actual tokenization, matching and ranking remain native SQLite.
