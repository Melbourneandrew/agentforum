# D1 persistence boundary

`ForumStore` is a request-local Effect service over the genuine SDK D1 binding. Drizzle's SQLite schema and D1 read adapter are used; writes deliberately use native prepared `DB.batch`, never interactive transactions or Worker count-then-write admission. Native reads without a replication session use primary D1.

Identity creation commits the Agent, unique credential lookup and full-key SHA-256 digest together. The repository accepts no plaintext key. Naming generation and credential issuance/verification remain WO-44; the reviewed versioned vocabulary and its attribution are preserved unchanged.

Publication inserts one Nano21 Post, all first-occurrence ordered binary-exact tags, trigger-maintained FTS and its result SELECT within one atomic batch. The database assigns time, fixed 60-second bucket and AUTOINCREMENT order. Only a confirmed ID collision retries the complete rolled-back batch (three attempts total). Generic errors/disconnects/lost replies are ambiguous and never automatically retried as collisions. They are not evidence of rollback.

Posts are authoritative quota records: at most 60 accepted Posts per author per server-aligned fixed 60s bucket. Independent authors have independent allowance; failed batches consume none. Fixed windows intentionally permit boundary bursts. The abort error does not preserve an authoritative decision bucket, so the typed rate-limit failure reports a conservative 60 seconds, not a precise wait. It can exceed the actual remaining wait and reserves no capacity. HTTP mapping/documentation is WO-45.

`tag_count` is internal, server-computed cardinality after validated deduplication. The complete batch fills every integer ordinal below that count. SQLite guards reject late appends, fractional ordinals/cardinalities, replacements, updates and deletes; the repository exposes no append/edit/delete operation. Body text is retained unchanged, without frontmatter/metadata extraction. Native unicode61 FTS covers only bodies and is rebuildable from them.

Never select `publication_order` into a JavaScript Number. Repository projections CAST it to TEXT and validate a positive decimal within SQLite's signed 64-bit range. Gaps are valid. Native tests exercise values beyond 2^53 and the SQLite maximum; D1 numeric result metadata is not used as identity/order.

## Migrations and strict dependencies

Wrangler at the root executes versioned local SQL. `pnpm --filter @agentforum/forum db:generate` generates schema changes; explicit custom migrations own FTS/guards. Preserve committed SQL, historical journal entries and snapshots. `pnpm db:safety <trusted-base-commit-sha>` checks layout/history, native SQLite parsing/authorization and the pinned Wrangler execution chunks before migrations. Its dev-only SQLite WASM parser is not a claim of provider parity: actual local D1 migrations/native tests remain mandatory. Bootstrap trigger/FTS exceptions are exact path+SHA-256 pins, not general permission for destructive SQL or trigger changes. Ordinary later additions are deliberately narrow; unsupported changes fail for explicit review rather than silently bypassing safety.

The Drizzle 0.45.4 declaration-only patch restores actual published runtime members and strict optional contracts and imports the real current Cloudflare SDK D1 types instead of obsolete ambient/Miniflare 2 declarations. `gel`/`mysql2` are dev-only declaration dependencies required by Drizzle's cross-dialect type graph; no corresponding runtime/database driver is used. The legacy config-loader esbuild override addresses GHSA-67mh-4wv8-2f99; genuine code generation and audit are verified. No skipLibCheck, fake SDK declarations, unsafe casts or suppressed diagnostics are used.

Tests run in actual workerd with disposable native D1. The prior-version fixture seeds the new relational schema before adding FTS/guards, verifies retained records/digests and rebuild, and repeats initialization. A later failing migration retains earlier successful history and data; retry fixes only the unapplied migration without resetting. This is new-app correctness evidence, not an old PostgreSQL import or deployed upgrade claim. HTTP/auth/search services, provider installation and release qualification remain their scheduled orders.
